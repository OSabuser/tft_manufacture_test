# test_sul_uim

## Модуль под тестом

`firmware/tft_app/src/domain/sul/uim/src/uim.c` — чистый декодер протокола
УИМ-6100 (ARCH.md §6/§8, Фаза 8), порт из
`firmware/tft_app/OLD_PROJECT_TFT4_UIM/source/main_programm.c`
(`msg_receiver_task`).

## Категория

A — платформонезависимый. `decode()` не делает ни одного HAL-вызова: вход —
только `sul_frame_t`, выход — только `sul_result_t`; всё состояние между
кадрами живёт в переданном `uim_ctx_t`, время/таймеры не используются
(гистерезис считается в КАДРАХ, не в миллисекундах — поэтому детерминирован).

## Отличия от НКУ-CAN, важные для тестов

- **Один тип кадра**, не PACKET1..5: заголовок `0x81 0x00` + W_0..W_3
  (`data[2..5]`).
- **CAN ID кадра РАВЕН адресу индикатора** (не база+сдвиг): 1..40 — этажный
  индикатор, 46..50 — роли кабины/главного этажа. Отсюда `cop_mode` и
  `should_respond`.
- **Один байт W_2 несёт ДВА смысла** — код этажа ЛИБО код спецрежима,
  различаются диапазоном.
- **Бит «нужен отклик» (W_3 бит 7) активен НУЛЁМ** — инверсия неочевидна.

## Что проверяется

**Гейтинг кадра** (порядок проверок — по контракту `sul.h`):
- чужой CAN ID → `IGNORED`;
- наш ID, но длина ≠ 6 → `ERR` (малформированный);
- наш ID и длина, но заголовок ≠ `0x81 0x00` → `IGNORED` (другой класс
  сообщения от той же станции, не ошибка).

**Коды этажей (W_2):** `0` → `"0"`, однозначные, двузначные, `40` (граница
положительных), `41`→`"-1"`, `49`→`"-9"`; код `50` (резерв) не меняет позицию.

**Сигналы (W_3):** направление `0/1/2/3` → `NONE`/`DOWN`/`UP`/`DOUBLE`; биты
гонга (`0x04`) и движения (`0x10`) — выставляются и снимаются.

**Роли адресов:** `cop_mode` истинен для 46/50 (кабина) и ложен для
47/48/49/этажных; отклик обязателен только для 46/47/48 и только при СБРОШЕННОМ
бите; для прочих ролей — никогда.

**Спецрежимы:** отображение кода на флаг (51 сейсмо, 53 пожарные, 55 сервис,
**56 эвакуация**, 57 пожар, 59 погрузка; 52/54/58 → **авария**); «последний
победил» (двух режимов одновременно не бывает). Под «Эвакуацию» и «Аварию» в
модель добавлены `sul_result_t.evacuation` / `SUL_MODE_EVACUATION` и
`SUL_MODE_ERROR` + строки в `k_mode_priority[]` (обе выше перегруза, см.
[MODE_PRIORITY.md](../../docs/tft_app/MODE_PRIORITY.md)) + метки в
`fallback.c` — без этого декодер удерживал бы режим, а резолвер отдавал
`NORMAL`, т.е. обычный этаж во время эвакуации/аварии.

**Исходящий отклик станции** (`uim_take_pending_tx()`, generic-канал
`sul_take_pending_tx_fn_t`): кадр `0x81 0x00` (2 байта) на CAN ID
«адрес + 0x80»; ID следует за настройкой адреса, а не захардкожен; отсутствует
при УСТАНОВЛЕННОМ бите W_3.7 и для ролей вне 46/47/48; **one-shot** (повторный
`take` отдаёт `false`); **транзитен** — кадр, отброшенный гейтом, гасит отклик
от предыдущего (иначе устаревший отклик уехал бы в шину повторно).

**ГИСТЕРЕЗИС удержания спецрежима** (ядро набора — порт
`special_mode_en_cnt`). Существует потому, что станция ЧЕРЕДУЕТ кадры «код
режима / код этажа» в одном и том же байте W_2: без удержания индикация мигала
бы с частотой шины. Асимметрия: ATTACK `+6` за кадр режима, RELEASE `−2` за
кадр обычного этажа → ровно **3** «этажных» кадра гасят режим, взведённый
**одним**.

Из эталона перенесена ТОЛЬКО протокольная часть. Заморозка направления и
глушение звука — специфика ЕГО презентации (режим и стрелка делили один слот
вывода `icon_img_ptr`; звук гасился тем же счётчиком) — сознательно НЕ
перенесены: здесь режим и стрелка независимые поля модели, layout выводит их
одновременно, а звук — забота `audio_policy` (Фаза 6).

- режим взводится одним кадром;
- двух «этажных» кадров НЕ хватает; третий — гасит, причём ВСЕ флаги разом;
- **чередование режим/этаж держит режим неограниченно** (тот самый регресс,
  ради которого механизм и существует);
- позиция продолжает обновляться «под» удерживаемым режимом;
- **направление тоже продолжает обновляться** под удерживаемым режимом (и
  берётся из кадра спецрежима, если тот несёт стрелку) — заморозки НЕТ;
- гонг/движение читаются всегда, даже под режимом;
- подземные этажи тоже отпускают удержание;
- код `50` не двигает счётчик ни в одну сторону;
- насыщение потолком (500): долго висящий режим гаснет не более чем за 250
  «этажных» кадров — 249 ещё держит, 250-й отпускает.

**Перегруз** (код сообщения W_1 = `0x39`): выставляет `overload` и взводит тот
же гистерезис; в кадре С обычным этажом ATTACK идёт ДО RELEASE (итог `+4`,
режим держится) — тест фиксирует порядок; перегруз и режим из кода этажа —
независимые владельцы, сосуществуют.

## Не покрыто (осознанно)

- **Фактическая отправка** отклика в шину (`sul_transport_can_send()` →
  `bsp_can_send()`) — transport/HW, host не тестируется. Покрыто ФОРМИРОВАНИЕ
  кадра; проводка «взять и отправить» — app-слой (`task_sul_rx.c`).
- **HW RX-фильтр CAN** под адрес индикатора — transport-слой, host не
  тестируется (та же слепая зона, что описана в ADDING_PROTOCOL.md §6).
- **Коды сообщений озвучки** (двери, движение, кнопка) — Фаза 6
  (`audio_policy`), на `sul_result_t` не влияют.
