# Отчёт: некэшируемый XIP, зависания и диагностика отказов

Разбор двух симптомов, оказавшихся одной причиной, и построенной по ходу
диагностической инфраструктуры. Затрагивает **все** образы репозитория
(bootloader, firmware_test, tft_app), а не только `tft_app`.

Дата разбора: 2026-08-05. Стенд: MIMXRT1052 + TFT8 (800×600), MCU-Link VCOM.

---

## 1. Симптомы

| # | Что наблюдалось | Кто заметил |
| --- | --- | --- |
| A | Плата перезагружается при правке адреса в меню. В простое (меню открыто, кнопки не нажимаются) — стабильна | пользователь, стенд |
| B | Отзывчивость меню ~1 с на нажатие. Оценено как «дикий регресс относительно старых проектов» | пользователь, стенд |

Симптом A выглядел как «не кормим watchdog»: WDOG взводит загрузчик с
таймаутом **10 с** (`firmware/bootloader/src/main.c`, WDE — write-once),
приложение только кормит.

---

## 2. Почему разбор занял несколько итераций

Три гипотезы были отброшены, и это стоило времени — фиксирую, чтобы не
повторять:

| Гипотеза | Чем отброшена |
| --- | --- |
| Гейт `!g_menu_active` в `sul_rx_task` пропускает кормление | `bsp_wdog_refresh()` безусловный и первый в цикле — гейт его не затрагивает |
| QSPI erase/write при сохранении настроек блокирует систему | пользователь уточнил: сохранения не было, только инкремент значения кнопкой |
| Флуд QSPI-чтений из `log_slot_status()` при холостом прокруте цикла | в простое меню плата стабильна — значит флуд сам по себе безвреден |
| PXP/LCDIF работают через семафор, а в эталоне — через прерывания | в `OLD_PROJECT_TFT8_UKL/source/display/pxp_config.c` **тот же** `while (!(kPXP_CompleteFlag & …)) {}` и тот же семафор от LCDIF ISR. Переделывать нечего |

**Вывод по методологии:** оценки «на глаз» давали десятки мс, а реальность —
940 мс, то есть ошибка на порядок с лишним. Дальше двигались только замерами.

## 3. Найденные дефекты — по порядку обнаружения

### 3.1. Диагностика: три разных отказа выглядели одинаково

`vApplicationStackOverflowHook` и `vApplicationMallocFailedHook` делали
`taskDISABLE_INTERRUPTS(); for(;;){}` — плата немо зависала, и через 10 с её
добивал watchdog. `HardFault_Handler` из startup — тоже бесконечный цикл.
Итого «сброс по WDOG», «переполнение стека» и HardFault были неразличимы без
отладчика, хотя лечатся по-разному.

Плюс `bsp_wdog_caused_last_reset()` в приложении всегда возвращал `false`:
флаг выставляется внутри `bsp_wdog_init()`, а её вызывает только загрузчик.

**Исправлено** — см. §4.1.

### 3.2. Фиктивный отсчёт времени в `sul_rx_task`

```c
elapsed_ms      += WDOG_FEED_PERIOD_MS;   /* предполагает 100 мс на итерацию */
since_status_ms += WDOG_FEED_PERIOD_MS;
```

Вне меню допущение верное — `bsp_can_receive()` съедает таймаут busy-spin'ом.
**Под меню** CAN-блок пропускается, итерация становится микросекундной, а
`vTaskDelayUntil()` при просроченном дедлайне не блокирует вовсе. «Миллисекунды»
бежали в сотни раз быстрее реального времени: heartbeat частил, а
`log_slot_status()` — это **чтения QSPI** — вызывался вместо раза в 2 с десятки
раз в секунду.

Видно в логах до/после: интервалы `periodic` были 2117/2493 мс, стали ровные
2000.

### 3.3. `LOG_I` в контексте демона программных таймеров

`dispatcher_poll()` → `log_transition()` → `LOG_I` → `vsnprintf` исполнялись в
демоне таймеров, у которого `configTIMER_TASK_STACK_DEPTH` = **1 КБ** против
4 КБ у app-задач (`APP_TASK_STACK_WORDS`). Риск переполнения стека, а хук
переполнения (см. §3.1) зависал молча.

### 3.4. Безусловные ожидания в present-пути `gfx`

```c
PXP_ClearStatusFlags(PXP, kPXP_Axi0ReadErrorFlag);    /* сбрасываем… */
PXP_ClearStatusFlags(PXP, kPXP_Axi0WriteErrorFlag);
PXP_Start(PXP);
while ((kPXP_CompleteFlag & PXP_GetStatusFlags(PXP)) == 0U) { }   /* …и не проверяем */
…
xSemaphoreTake(s_frame_done, portMAX_DELAY);
```

Флаги AXI-ошибок сбрасывались перед пуском и после **никогда не читались**.
При AXI-ошибке `CompleteFlag` не появится никогда — busy-spin занимает CPU
навсегда. Поскольку он исполняется в `render_task` (приоритет `+2`), а кормит
watchdog `sul_rx_task` (`+1`), кормилец не получал CPU уже никогда.

Ожидание FRAME_DONE с `portMAX_DELAY` CPU не отнимает (блокирующее), но при
потере прерывания вешало рендер молча навсегда.

### 3.5. Корневая причина обоих симптомов: XIP-флеш размечен как Device memory

`board_mpu_init()` (`bsp/generated/board.c`):

```c
/* Region 2: Device, 0x60000000, 512 MB. */
MPU->RASR = ARM_MPU_RASR(0U, AP_FULL, 2U, 0U, 0U, 0U, 0U, SIZE_512MB);  /* TEX=2,C=0,B=0 */

#if defined(XIP_EXTERNAL_FLASH) && (XIP_EXTERNAL_FLASH == 1)
    /* Region 3: Normal WB, RO, XIP — overrides Region 2 for Flash 64 MB. */
    MPU->RASR = ARM_MPU_RASR(0U, AP_RO, 0U, 0U, 1U, 1U, 0U, SIZE_64MB);
#endif
```

Код приложения исполняется из `0x60040000` — внутри Region 2. `TEX=2,C=0,B=0` —
это **Device memory**: не кэшируется, не префетчится, доступ строго упорядочен.
То есть **каждая выборка инструкции идёт в QSPI через FlexSPI, I-Cache
бесполезен**.

Кэшируемый Region 3 перекрыл бы это, но он под `#if`, а макрос до `board.c` не
доходил:

```cmake
# bsp/CMakeLists.txt — было
add_library(bsp_board STATIC generated/board.c generated/pin_mux.c)
target_compile_definitions(bsp_board PUBLIC CPU_MIMXRT1052CVJ5B)   # и всё

add_library(bsp_boot_xip_no_dcd INTERFACE)
target_compile_definitions(bsp_boot_xip_no_dcd INTERFACE XIP_EXTERNAL_FLASH=1 …)
```

`XIP_EXTERNAL_FLASH=1` раздают INTERFACE-цели `bsp_boot_xip*`, и firmware-цели
(`app`, `bootloader`) их линкуют. Но определения INTERFACE-библиотеки доходят
только до тех целей, которые её линкуют — то есть до собственных исходников
`app`, а **не** до `board.c`, который компилируется в отдельной статической
библиотеке `bsp_board`. Region 3 вырезался препроцессором **во всех образах,
включая загрузчик**.

Не замечали потому, что до тяжёлого CPU-рендера меню это никого не жало:
доменная логика и разбор CAN-кадров дёшевы, а PXP — железо, ему CPU не нужен.

**Подсказка, закрывшая вопрос** (от пользователя): в старых проектах код
исполнялся из SDRAM, размеченной Normal WB — отсюда и «отличный перфоманс».

## 4. Что сделано

### 4.1. Крэш-запись, переживающая сброс

`firmware/tft_app/src/app/crash_log.{h,c}` + секция `.noinit` в
`cmake/linker/MIMXRT1052xxxxx_app_slot.ld`.

Запись лежит вне `[__bss_start__..__bss_end__]`, поэтому startup её не
обнуляет (проверено: цикл очистки строго `<`, а секция имеет флаг только
`ALLOC` — в образе места не занимает), а DTCM сохраняет содержимое через сброс
ядра. Хуки и `HardFault_Handler` пишут причину и уходят в `NVIC_SystemReset()`
немедленно — не ждём 10 с watchdog'а.

- `HardFault_Handler` — `naked` + asm, достаёт из кадра исключения **PC и LR**.
- `bsp_wdog_reset_was_timeout()` — новая функция BSP, читает `WDOG1->WRSR`
  напрямую, без `bsp_wdog_init()`.
- `crash_log_report_previous()` печатает вердикт при старте.

Четыре взаимоисключающих вердикта:

| Строка в логе | Диагноз |
| --- | --- |
| `STACK OVERFLOW task='X'` | переполнение стека задачи X |
| `HARDFAULT pc=0x… lr=0x…` | отказ в коде; адрес искать в `app.map` |
| `STARVATION … залипли в '<крошка>', без кормления N мс` | кормилец WDOG не получал CPU |
| `WATCHDOG TIMEOUT (крэш-записи нет)` | голодание, которое не поймал детектор |
| `предыдущий сброс: штатный (POR/внешний)` | нормальный старт |

**Ограничение:** запись живёт в DTCM и **теряется при снятии питания** (POR).
После зависания перезапускать программно/кнопкой reset, не по питанию.

### 4.2. Детектор голодания + «хлебные крошки»

`sul_rx_task` отмечается `crash_log_feed_mark()`; проверку делает
`crash_log_check_starvation()` из `input_poll_cb` — в контексте демона
таймеров, который **нельзя выголодать** (высший приоритет в системе). Порог
4 с против 10 с у watchdog: успеваем записать причину сами.

`crash_log_set_breadcrumb()` расставлен вокруг долгих участков:
`render:menu-open`, `render:menu-nav`, `render:indication`,
`menu:settings-save`. Именно крошка назвала виновника:

```
STARVATION (кормилец WDOG не получал CPU) залипли в 'render:menu-nav', без кормления 4003 мс
```

### 4.3. Ограниченные ожидания в `gfx`

`gfx_pxp_run()` возвращает `bool`, проверяет флаги AXI-ошибок и имеет бюджет
`GFX_PXP_TIMEOUT_MS` = 500 мс (замер полного композита — 66 мс, запас ×7).
Ожидание FRAME_DONE — `GFX_VSYNC_TIMEOUT_MS` = 200 мс. При неудаче свап не
делается, счётчик `g_gfx_present_errors` инкрементируется, система остаётся
живой. Плюс `g_gfx_last_pxp_ms` / `g_gfx_last_vsync_ms` для диагностики фаз.

### 4.4. Исправление корневой причины

```cmake
# bsp/CMakeLists.txt — стало
target_compile_definitions(bsp_board PRIVATE XIP_EXTERNAL_FLASH=1)
```

Region 3 теперь компилируется, флеш размечен Normal WB RO, I-Cache работает.
Проверено по объектному файлу: присутствуют оба RBAR-значения — `0x60000012`
(Region 2, Device) и `0x60000013` (Region 3, кэшируемое перекрытие); до правки
второго не было.

Регион RO и покрывает физический флеш, поэтому корректен для любого образа
независимо от того, исполняется он XIP или из RAM. Записи во флеш идут
IP-командами FlexSPI (`bsp_qspi_flash`), а не через этот AHB-регион.

### 4.5. Прочее

- **Реальные тики** вместо фиктивных счётчиков в `sul_rx_task` (§3.2), со
  знаковой разницей — корректно при перевороте счётчика.
- **`LOG_I` убран из демона таймеров** (§3.3): логирование фронтов диспетчера
  переехало в `render_task`, который будится тем же событием и имеет полный стек.
- **`gfx_fill_rect` построчно** вместо двойного цикла по `set_pixel` — был
  вызов функции плюс две проверки границ на каждый из ~103 тыс. пикселей кадра.
  Приведено к виду уже существовавшего `gfx_clear_rect`.
- **Комментарий про таймаут WDOG исправлен**: 10 с от загрузчика, а не «>= 1 c».

## 6. Что осталось незакрытым

### 6.1. Кормление watchdog зависит от самой низкоприоритетной задачи

`bsp_wdog_refresh()` вызывается из **единственного** места —
`task_sul_rx.c`, — а `sul_rx_task` имеет приоритет `+1`, ниже демона таймеров,
`menu_task` (`+3`) и `render_task` (`+2`). Любой долгий участок выше `+1`
по-прежнему валит плату.

Сейчас это **прикрыто, но не защищено**: детектор голодания (§4.2) даёт
диагноз и управляемый сброс вместо молчаливого. Правильный фикс — heartbeat-
супервизор: кормит демон таймеров, но только если все наблюдаемые задачи
отметились. Меняет смысл гарантии watchdog (с «жива задача-кормилец» на «живы
все наблюдаемые»), поэтому требует явного решения.

### 6.2. Оставшийся потенциал по отзывчивости

Если 21 мс когда-нибудь окажется мало:

1. **Debug — это `-O0`**, Release — `-O1` (`cmake/toolchain_arm.cmake`). При
   `-O0` `static inline set_pixel`/`blend_pixel` не инлайнятся, `s_fb_width`
   перечитывается из памяти на каждый пиксель. Сравнение Debug-образа с
   боевыми старыми сборками некорректно по определению.
2. **Перерисовка только изменившихся строк.** Сейчас на каждое движение
   курсора перерисовывается всё окно, хотя меняются две строки — старая и
   новая. Оконный present у нас уже есть, логично сделать и оконное рисование.
3. **Двойная запись окна**: сначала `memset` всех 480×272, потом поверх
   заливаются фоны 6 строк.

### 6.3. Временная диагностика в горячем пути

`LOG_I` с замером `menu-nav` в `task_render.c` — отладочный, добавлялся под эту
задачу. Убрать или перевести в `LOG_D`, когда тема будет закрыта окончательно.

## 7. Выводы для будущих разборов

1. **Определения INTERFACE-целей CMake не доходят до соседних статических
   библиотек.** Если макрос влияет на код в `bsp_board`, он должен быть задан
   у `bsp_board`. Этот класс ошибки молчалив: препроцессор просто вырезает
   блок, ни предупреждения, ни ошибки линковки.
2. **Симптом «не кормим watchdog» почти никогда не означает буквально это.**
   Стоит сначала научиться различать отказы (крэш-запись + причина сброса),
   и только потом чинить.
3. **Единственная точка кормления в низкоприоритетной задаче — конструктивная
   хрупкость**, а не деталь реализации.
4. **Безусловные ожидания (`while(!flag){}`, `portMAX_DELAY`) в
   реальном времени — дефект по умолчанию.** Особенно когда рядом сбрасываются
   флаги ошибок, которые потом не проверяются.
5. **Замер дешевле трёх гипотез.** Здесь три итерации догадок против одного
   прогона с инструментацией, который дал ответ сразу.
