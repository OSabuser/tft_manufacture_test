# Чек-лист: проверка `firmware_test` и `bootloader` после фикса кэшируемого XIP

Разовый чек-лист под конкретную правку в ветке `dev`. Не путать с общим
порядком выпуска — тот в [RELEASE_PROCESS.md](RELEASE_PROCESS.md).

**Что проверяем.** Фикс из [PERF_AND_HANG_INVESTIGATION.md](PERF_AND_HANG_INVESTIGATION.md):
`bsp_board` не получал `XIP_EXTERNAL_FLASH=1`, из-за чего Region 3 MPU
вырезался препроцессором и флеш оставался **Device memory** — инструкции не
кэшировались во всех образах, включая загрузчик.

**Почему нужен отдельный прогон, а не «собралось и ладно».** Правка меняет
атрибуты памяти, из которой исполняется код. Она не может сломать логику, но
может вскрыть латентные проблемы когерентности — и ровно одну такую вскрывает
гарантированно (см. §1).

---

## 0. Состав правки в `dev`

Правка должна быть **двумя частями**. Одной первой — нельзя.

- [ ] `bsp/CMakeLists.txt` — `target_compile_definitions(bsp_board PRIVATE XIP_EXTERNAL_FLASH=1)`
- [ ] `firmware/bootloader/src/boot_select.c` — обслуживание кэшей в
      `cleanup_before_jump()` (см. §1)

> Из ветки `tft-app-dev` в `dev` переносится **только это**. Всё остальное там
> (УИМ, диагностика `crash_log`, `.noinit`, изменения `gfx`/`bsp_can`/`bsp_wdog`)
> к релизу `firmware_test`/`bootloader` отношения не имеет и поедет своим
> порядком, когда Фаза 8 закроется.

## 1. Обязательная сопутствующая правка: кэши перед прыжком

**Это не «желательно», это условие безопасности релиза.** Проверено по коду:

- `cleanup_before_jump()` ([boot_select.c](../firmware/bootloader/src/boot_select.c))
  не трогает кэши вообще — ни инвалидации, ни отключения.
- `bsp_qspi_flash` не делает обслуживания кэшей CPU: `qspi_sw_reset()` сбрасывает
  AHB-буфер FlexSPI, а не L1 Cortex-M7.
- `jump_to_image()` читает таблицу векторов **прямым разыменованием**
  (`p_vt->msp`, `p_vt->reset`) — то есть через AHB-окно, теперь кэшируемое, — и
  сразу начинает исполнять код оттуда.
- Загрузчик **пишет флеш и прыгает в той же сессии, без сброса**, на двух путях
  ([main.c](../firmware/bootloader/src/main.c)):
  - `sd_update_check()` поставил образ с SD → `jump_now()`;
  - `RECOVERY_ERASE_ACTIVE_THEN_BOOT_OTHER`: `flash_area_erase()` всего слота →
    `jump_now()`.

До фикса флеш был Device memory — кэширование невозможно, риска не было. После
фикса появляются устаревшие строки I-cache для только что перезаписанного
региона. Дырявых D-cache строк не будет (Region 3 — RO), но stale I-cache
достаточно, чтобы исполнить мусор. Класс отказа — «кирпич после обновления».

Минимум: `SCB_CleanInvalidateDCache()` + `SCB_InvalidateICache()` в
`cleanup_before_jump()` перед `__DSB()/__ISB()`.

> Референс SDK (`boot/nxp_mcux_sdk/boot.c::do_boot()`) обслуживания кэшей тоже
> не делает — на него в этом вопросе не опираться, он выезжает на том, что
> валидация идёт IP-командами, а мы дополнительно разыменовываем и исполняем.

## 2. Сборка (devcontainer)

- [ ] `just build::build-all-release` — все три firmware-проекта собираются
- [ ] `just build::test-host` — host-тесты зелёные
- [ ] `just build::test-host-release` — то же в Release-профиле
- [ ] Нет новых предупреждений компилятора

Проверка, что Region 3 действительно попал в объект (без этого фикс не
работает, а сборка при этом успешна — молчаливый режим отказа):

```bash
docker exec -w /workspace tft-devcontainer bash -c \
  "/opt/arm-toolchain/bin/arm-none-eabi-objdump -d \
   /workspace/build/Release/bsp/CMakeFiles/bsp_board.dir/generated/board.c.obj \
   | grep -E '0x6000001[23]'"
```

- [ ] Видны **оба** значения: `0x60000012` (Region 2, Device) и `0x60000013`
      (Region 3, кэшируемое перекрытие). Если второго нет — макрос не доехал.

## 4. `bootloader` — обычная загрузка

- [ ] Прошивается по SWD, стартует
- [ ] Слот A с валидным подтверждённым образом → прыжок, образ работает
- [ ] Слот Б с валидным образом → прыжок, образ работает
- [ ] Оба слота пусты → остаётся в ожидании SD (не уходит в recovery ложно)
- [ ] LED-индикация соответствует [LED_PATTERNS.md](bootloader/LED_PATTERNS.md)
      (если статусы менялись — сверить)

## 5. `bootloader` — пути записи флеша (КРИТИЧНО)

Здесь и проявится проблема когерентности, если правка §1 не сделана или
сделана неверно. Каждый пункт — установка/стирание с последующим **прыжком в
той же сессии**, без промежуточного сброса.

- [ ] **Обновление с SD:** вставить SD с более новым образом → загрузчик
      ставит его → прыгает → **образ реально стартует и работает**, а не виснет
      и не уходит в hardfault
- [ ] Повторить 3–5 раз подряд (проблема когерентности может быть плавающей)
- [ ] **Recovery-режим:** войти принудительно (кнопка) → поставить образ с SD →
      прыжок → образ работает
- [ ] **Стирание зависшего слота** (`RECOVERY_ERASE_ACTIVE_THEN_BOOT_OTHER`):
      довести счётчик попыток до порога → загрузчик стирает подозрительный слот
      → прыгает в фолбэк → **фолбэк-образ работает**
- [ ] **Downgrade** (если поддерживается кнопкой): установка более старого
      образа → прыжок → работает
- [ ] После каждой установки — перезагрузка по питанию и проверка, что образ
      грузится и со «холодного» старта тоже

> Если хоть один пункт §5 падает — **не релизить**. Это ровно тот отказ, ради
> которого §1 и существует.
