# Аппаратная верификация загрузчика

Полный ручной прогон загрузчика на стенде, на образах-заглушках вместо `tft_app`.
Шесть блоков: обычная загрузка, установка с SD, recovery, откат, регрессия по USB ROM.

Когда прогонять:

- перед релизом загрузчика;
- после правок, затрагивающих память, кэш, MPU, тактирование или карту флеша —
  то есть всего, что может сломать прыжок, оставаясь «зелёным» на host-тестах;
- после правок в `boot_select`, `sd_update`, `recovery`, `update_policy`,
  `flash_map_backend`, `bsp_qspi_flash`.

Логика `update_policy` и `recovery` целиком покрыта host-тестами
(`just build::test-host`) — здесь проверяется то, чего host-тесты не видят:
реальный прыжок, реальный флеш, реальные тайминги watchdog.

Все команды — из корня репозитория. Сборка — в devcontainer, прошивка и
наблюдение — на хосте.

---

## 0. Почему заглушки, а не `tft_app`

Стабы линкованы под конкретный слот и мигают `LED_APP` с разной частотой, поэтому
факт «прыжок состоялся и исполняется код именно того слота» виден глазами, без
CDC и отладчика. Плюс есть варианты с детерминированным зависанием на разных
стадиях — ими воспроизводятся классы отказов, которые на живом приложении
пришлось бы ждать случайно.

Заглушки USB не поднимают. **Исчезновение CDC-порта — сам по себе признак того,
что прыжок произошёл**; пока порт есть, работает загрузчик.

## 1. Сборка

```bash
just build::build-bootloader-release
just build::hab-bootloader-release
just build::build-mcuboot-stub
```

Стабы собираются и подписываются только в Debug — это полезная нагрузка, её
профиль на проверку не влияет. Загрузчик берём тот, который релизится.

В `build/Debug/signed/` — семь файлов ровно по 2 МБ:

| Файл | Версия | Слот линковки | `--confirm` | Поведение в рантайме |
| --- | --- | --- | --- | --- |
| `stub_a_v1_confirmed.bin` | 1.0.0 | A (`0x60040000`) | да | здоров, мигает ~1/сек |
| `stub_b_v2_confirmed.bin` | 2.0.0 | Б (`0x60240000`) | да | здоров, мигает ~2/сек |
| `stub_a_v1_unconfirmed.bin` | 1.0.0 | A | нет | здоров; см. §9, ограничение 1 |
| `stub_a_hang_class_a.bin` | 1.0.0 | A | нет | **Класс A**: не подтверждается, виснет сразу |
| `stub_b_hang_class_a.bin` | 2.0.0 | Б | нет | то же для Slot Б |
| `stub_a_confirm_hang_class_b.bin` | 1.0.0 | A | да | **Класс B**: подтверждается, виснет через ~6 с |
| `stub_b_confirm_hang_class_b.bin` | 2.0.0 | Б | да | то же для Slot Б |

Подписаны тестовым sample-ключом MCUboot
(`sdk/middleware/mcuboot_opensource/root-ec-p256.pem`) — публичным, не
production. Поведение задаётся осями `STUB_CONFIRM_MODE` / `STUB_HANG_MODE` /
`STUB_FEED_WDOG`, см. [CMakeLists.txt](CMakeLists.txt) и [main.c](main.c).

## 2. Правила стенда

Нарушение любого из них даёт ложный «провал» — симптом при этом неотличим от
настоящего отказа прыжка.

**Стабы не PIC.** Абсолютные адреса зашиты при линковке. Файл обязан быть
слинкован под тот слот, куда он реально попадёт. Положить «не тот» — крипто-гейт
пройдёт (подпись валидна для содержимого независимо от адреса), установка
отрапортует успех, а исполнится код с чужими адресами.

**Целевой слот выбирает политика, а не оператор.** `update_policy_decide()`
ставит всегда в **НЕактивный** слот; на чистой плате активного нет, поэтому
целевой — Slot A. В recovery целевой слот **всегда A** независимо ни от чего.
См. [update_policy.c](../src/update_policy.c).

**Активный слот определяется версией.** `boot_go()` выбирает более высокую.
Поэтому образ, который должен зависнуть, обязан иметь версию **выше** фолбэка:
зависающий — в Slot Б (2.0.0), фолбэк — в Slot A (1.0.0). Наоборот сценарий
ничего не покажет.

**Между сценариями — power cycle.** Ни SWD-запись, ни pyOCD-стирание плату не
ресетят. Нужен настоящий POR, а не ресет отладчиком: счётчик попыток обнуляется
именно по `IPP_RESET_B`.

**Кнопки сэмплируются один раз на старте.** `BSP_BUTTON_1` (даунгрейд) и
`BSP_BUTTON_2` (recovery) читаются сразу после `bsp_button_init()`, до всей
SD-логики, и защёлкиваются на сессию. Держать нужно **в момент подачи питания**;
долгое удержание не требуется, отпускать можно сразу.

## 3. Операции

### 3.1 Прошивка загрузчика

```bash
just host::flash-swd-bootloader-release
```

После — обязательный power cycle. Debug-вариант: `flash-swd-bootloader-debug`
(добавляет DEV-команду `sdram_test`, в остальном путь тот же).

### 3.2 Запись образа в слот

Не через `flash_swd.py` — он собирает FCB+IVT+HAB под `0x60000000`, слотам это не
нужно. Пишем сырой подписанный `.bin` прямо по адресу слота.

> `uv run --directory tools/hil` меняет рабочую директорию у самого `pyocd`, а не
> только у `uv` — путь к `.bin` должен быть абсолютным (`"$(pwd)/..."`), иначе
> резолвится от `tools/hil/`.

```bash
uv run --directory tools/hil pyocd flash --target mimxrt1050_quadspi --frequency 4000000 \
  --base-address 0x60040000 --erase sector "$(pwd)/build/Debug/signed/<файл>.bin"   # Slot A

uv run --directory tools/hil pyocd flash --target mimxrt1050_quadspi --frequency 4000000 \
  --base-address 0x60240000 --erase sector "$(pwd)/build/Debug/signed/<файл>.bin"   # Slot Б
```

### 3.3 Стирание слота

Адрес — позиционный аргумент, диапазон в формате `start+length`.

```bash
uv run --directory tools/hil pyocd erase --target mimxrt1050_quadspi --frequency 4000000 \
  --sector 0x60040000+0x200000   # Slot A, 2 МБ

uv run --directory tools/hil pyocd erase --target mimxrt1050_quadspi --frequency 4000000 \
  --sector 0x60240000+0x200000   # Slot Б, 2 МБ
```

### 3.4 Подготовка SD-карты

FAT32/FAT16, файл в корне, имя ровно **`TFT_APP.BIN`** (загрузчик открывает
`2:/TFT_APP.BIN`, `2:` — внутренняя нумерация FatFS). Файл — подписанный стаб,
просто переименованный.

Карту можно вставлять и на ходу: загрузчик пере-сканирует её примерно раз в 1,5 с
в цикле ожидания, ресет для этого не нужен.

### 3.5 CDC

```bash
screen /dev/cu.usbmodemXXXX   # macOS, порт свой на каждое подключение
```

| Команда / событие | Смысл |
| --- | --- |
| `{"type":"cmd","cmd":"ping"}` → `{"type":"pong"}` | загрузчик жив |
| `{"type":"cmd","cmd":"wdog"}` | `recovered` (был ли последний сброс по WDOG), `reset_count`, `threshold` |
| `status: waiting_for_sd` | нет валидного слота, ждём карту |
| `status: installing` | идёт запись образа в слот |
| `status: update_skipped` | кандидат отклонён по версии |
| `status: recovery_mode` | плата в режиме восстановления |
| `{"ok":false,"error":"…"}` | `SD_CANDIDATE_INVALID`, `SD_INSTALL_WRITE_FAILED`, `SD_INSTALL_REJECTED`, `SD_DOWNGRADE_ERASE_FAILED` |

Полный протокол — [README.md](../README.md). LED-индикация загрузчика —
[LED_PATTERNS.md](../../../docs/bootloader/LED_PATTERNS.md); частоты `LED_APP`
у заглушек (~1/сек и ~2/сек) относятся к стенду и в том документе отсутствуют.

## 4. Блок 1 — обычная загрузка

Между сценариями — power cycle.

| # | Подготовка | Ожидаемо |
| --- | --- | --- |
| 1.1 | Slot Б стёрт (3.3); Slot A ← `stub_a_v1_confirmed.bin` | `LED_APP` ~1/сек |
| 1.2 | + Slot Б ← `stub_b_v2_confirmed.bin` | `LED_APP` ~2/сек (2.0.0 > 1.0.0) |
| 1.3 | Оба слота стёрты | `LED_APP` не горит, `HEARTBEAT` 50/450 мс, CDC `waiting_for_sd`, `ping`→`pong` |

В 1.3 оставить плату на 2+ минуты и запросить `wdog`: `reset_count` должен
остаться `0`. Пустая плата не должна уходить в recovery — счётчик не растёт там,
где пытаться нечего.

---

## 5. Блок 2 — установка с SD и прыжок в той же сессии

Самый нагруженный путь: загрузчик стирает слот, пишет 2 МБ, валидирует и **сразу**
прыгает — без промежуточного сброса.

Стартовое состояние — оба слота стёрты (после 1.3). Между раундами power cycle,
карту менять при снятом питании.

| # | `TFT_APP.BIN` | Кнопка | Активный до | Куда поставит | Что ещё | `LED_APP` после |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `stub_a_v1_confirmed.bin` | — | нет | **A** | — | ~1/сек |
| 2 | `stub_b_v2_confirmed.bin` | — | A (v1) | **Б** (новее) | — | ~2/сек |
| 3 | `stub_a_v1_confirmed.bin` | **BTN_1** | Б (v2) | **A** (даунгрейд) | стирает Slot Б | ~1/сек |
| 4 | `stub_b_v2_confirmed.bin` | — | A (v1) | **Б** | — | ~2/сек |
| 5 | `stub_a_v1_confirmed.bin` | **BTN_1** | Б (v2) | **A** | стирает Slot Б | ~1/сек |

Раунды 3 и 5 ценнее прочих: в одной сессии происходят два стирания (целевой слот
плюс прежний активный), запись и прыжок.

Пинг-понг нужен потому, что повторно поставить **ту же** версию нельзя — политика
даст `update_skipped` (равная версия не проходит ни как «новее», ни как
даунгрейд). Если менять файл на карте неудобно, есть вариант с отладчиком:
держать `TFT_APP.BIN` = `stub_a_v1_confirmed.bin` постоянно и между раундами
стирать Slot A (3.3), возвращая плату в состояние «чистая». Он проще, но не
покрывает установку в Slot Б и путь стирания прежнего активного слота.

**В каждом раунде наблюдать:**

1. CDC: `installing`.
2. `LED_APP` 250/250 мс на время установки, ~10–20 с. В фазе стирания мигание
   **дёрганое** — блок стирается под `qspi_irq_lock()`, SysTick на это время
   глохнет (см. [led_status.h](../src/led_status.h)). Не дефект.
3. CDC-порт исчезает — прыжок состоялся.
4. `LED_APP` выходит на ровную частоту из таблицы и держит её бессрочно.
5. Плата не ресетится каждые ~10 с и не уходит в recovery-паттерн.

Пункт 4 — ключевой: ровное мигание нужной частоты означает, что стаб дошёл до
главного цикла, то есть первая же выборка инструкций после прыжка была корректной.

**Финал блока:** вынуть карту, полностью снять питание, подать заново — образ
должен грузиться и с холодного старта.

## 6. Блок 3 — recovery по BTN_2

Порядок фаз важен: если карта будет вставлена уже на старте, установка произойдёт
на первой же попытке и подавление прыжка наблюдать не удастся.

**3.1 — приоритет кнопки.** Карту **не вставлять**. Удерживая `BSP_BUTTON_2`,
подать питание.

Ожидаемо: recovery немедленно, **без попытки прыжка** в валидный Slot A — то есть
`LED_APP` на ~1/сек не переходит. Оба светодиода мигают синхронно 100/100 мс, CDC
повторяет `recovery_mode` примерно раз в 1,5 с.

**3.2 — установка из recovery.** Питание не снимать. Вставить карту с
`TFT_APP.BIN` = **`stub_a_v1_confirmed.bin`** (recovery ставит только в Slot A).

Ожидаемо: в течение ~1,5 с — `installing`; стираются оба слота, образ пишется в
Slot A, прыжок в той же сессии; CDC-порт пропадает, `LED_APP` ~1/сек.

В recovery версия не проверяется вообще, поэтому тот же 1.0.0 поверх лежащего
1.0.0 установится штатно — это не «пропуск по версии».

## 7. Блок 4 — стирание зависшего слота и прыжок в фолбэк

Класс B: образ успевает подтвердить себя и виснет уже после этого, поэтому штатный
revert MCUboot не срабатывает — ловит `recovery.c` по счётчику WDOG-сбросов.
Порог — `RECOVERY_DEFAULT_THRESHOLD` = 3 ([recovery.h](../src/recovery.h)).

**Подготовка** (карта вынута):

```bash
uv run --directory tools/hil pyocd flash --target mimxrt1050_quadspi --frequency 4000000 \
  --base-address 0x60040000 --erase sector "$(pwd)/build/Debug/signed/stub_a_v1_confirmed.bin"

uv run --directory tools/hil pyocd flash --target mimxrt1050_quadspi --frequency 4000000 \
  --base-address 0x60240000 --erase sector "$(pwd)/build/Debug/signed/stub_b_confirm_hang_class_b.bin"
```

Один power cycle, дальше не вмешиваться ~50 с:

1. Выбран Slot Б (2.0.0 > 1.0.0). `LED_APP` ~2/сек первые ~6 с — образ жив и уже
   подтверждён.
2. `LED_APP` замирает. Через ~10 с — WDOG-сброс.
3. Цикл повторяется, `reset_count` растёт 1 → 2 → 3.
4. На третьем сбросе `recovery_decide()` находит валидный фолбэк → **стирает
   Slot Б** → прыжок в Slot A в той же сессии → `LED_APP` ~1/сек бессрочно.

CDC здесь ловить неудобно: порт то появляется на несколько секунд работы
загрузчика, то исчезает на время работы стаба. Картина по LED однозначна; если
нужна цифра — успеть отправить `wdog` в одном из окон.

## 8. Блок 5 — A/B и откат

**5.1 — подтверждённый образ не откатывается.** После любого раунда блока 2 сделать
power cycle: плата должна снова загрузиться в тот же слот, а не уйти в ожидание SD.

**5.2 — неподтверждённый образ откатывается на предыдущий слот.** Зависающий образ
обязан быть старше по версии, иначе `boot_go()` его не выберет.

```bash
uv run --directory tools/hil pyocd flash --target mimxrt1050_quadspi --frequency 4000000 \
  --base-address 0x60040000 --erase sector "$(pwd)/build/Debug/signed/stub_a_v1_confirmed.bin"

uv run --directory tools/hil pyocd flash --target mimxrt1050_quadspi --frequency 4000000 \
  --base-address 0x60240000 --erase sector "$(pwd)/build/Debug/signed/stub_b_hang_class_a.bin"
```

Карта вынута, один power cycle, ~15 с:

1. Выбран Slot Б, `copy_done` выставляется, прыжок. Стаб виснет **до** первого
   переключения LED — `LED_APP` не загорается вообще. Для Класса A это норма;
   отличие от настоящего отказа прыжка в том, что здесь зависание запрограммировано.
2. Через ~10 с — WDOG-сброс.
3. Вторая загрузка: `boot_go()` видит `copy_done=SET` при неустановленном
   `image_ok` → **стирает Slot Б** → выбирает Slot A → прыжок в той же сессии →
   `LED_APP` ~1/сек.

**Затем ещё один power cycle** — плата должна снова загрузиться в Slot A. Тем
самым подтверждается, что Slot Б действительно стёрт, а не пропущен на одном цикле.

> Revert — третий путь «стираем флеш и прыгаем в той же сессии»: стирание
> происходит внутри `boot_select_or_erase()` в `boot_go()`, а прыжок — сразу
> после возврата, без сброса. Первые два — установка с SD (§5) и
> `RECOVERY_ERASE_ACTIVE_THEN_BOOT_OTHER` (§7).

## 9. Блок 6 — регрессия по USB ROM

Плата в режиме Serial Downloader (BOOT_MODE = 01):

```bash
just host::flash firmware_test release
```

Затем — производственный путь service-tui с актуальным `bootloader_hab.bin`.

`flash_usb.py` пишет только контейнер от `0x60000000` (~65–70 КБ), слоты на
`0x60040000` и `0x60240000` не затрагиваются. Поэтому сразу после можно вернуть
загрузчик —

```bash
just host::flash bootloader release
```

— и он прыгнет в уцелевший стаб. Бесплатная финальная проверка согласованности
прошивки по USB ROM и пути загрузки.

## 10. Известные ограничения стенда

1. **`stub_a_v1_unconfirmed.bin` непригоден для revert-теста.** Файл подписан без
   `--confirm`, но собран из `test_slot_stub_a` с `STUB_CONFIRM_MODE=0` — образ
   подтверждает себя в рантайме через миллисекунды после прыжка, и на второй
   загрузке откатывать уже нечего. Revert проверяется Класс-A образом (§8).
   Здорового-но-никогда-не-подтверждающегося стаба (`CONFIRM_MODE=2`,
   `HANG_MODE=0`) в наборе нет; если понадобится изолировать revert от зависания
   — добавить такую цель в [CMakeLists.txt](CMakeLists.txt).
2. **CDC пропадает после прыжка** — заглушки USB не поднимают. Всё, что нужно
   прочитать по CDC, читается в окне работы загрузчика.
3. **Дёрганое мигание в фазе стирания** — известное ограничение индикации, не
   дефект (см. §5, пункт 2).
4. **Версии стабов фиксированы по слоту линковки** (1.0.0 = A, 2.0.0 = Б). Это
   ограничивает выбор комбинаций: зависающий образ всегда должен оказаться в
   Slot Б, фолбэк — в Slot A.
